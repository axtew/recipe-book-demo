# Architecture

How the app is put together: where the data on the screen comes from, what the browser stores, and how the PWA works offline. The decisions behind it are in [`decisions/`](decisions/README.md).

## System overview

```
phone / browser                       internet            Supabase (Singapore)
┌────────────────────────┐                        ┌──────────────────────────┐
│ App (React)            │                        │ GoTrue      — login      │
│   ↕                    │                        │ PostgREST   — API to DB  │
│ In-memory query cache  │◄──── HTTPS ───────────►│ Storage     — photos     │
│   ↕                    │                        │ PostgreSQL  — data + RLS │
│ IndexedDB — cache copy │                        └──────────────────────────┘
│ Cache Storage — code   │
└────────────────────────┘
```

There is no server code of our own. The client talks to Supabase directly, and PostgreSQL plays the role of the backend: it enforces access (RLS) and integrity (foreign keys, constraints). The reasons are in [ADR 0010](decisions/0010-supabase-without-own-backend.md). The static files are served by Cloudflare Workers Static Assets ([ADR 0013](decisions/0013-cloudflare-hosting.md)).

## Two browser storages

The app uses two independent storages, and they hold different things:

| | **Cache Storage** | **IndexedDB** |
|---|---|---|
| Holds | the app code: JS, CSS, HTML, icons, dictionaries | the data: products, recipes, cook log |
| Written by | the service worker (PWA) | TanStack Query through a persister |
| Purpose | the app **opens** without a network | the app **has data** without a network |
| Updated | when a new version is deployed | after every successful request to the database |

If the app opens offline but is empty, Cache Storage works and IndexedDB does not. If it does not open at all, it is the other way round.

## The data cache

### How the cache reaches IndexedDB

The app never touches IndexedDB directly. The chain is:

```
IndexedDB
   ↑
idb-keyval — a thin wrapper with get / set / del
   ↑
@tanstack/query-async-storage-persister — writes the cache to any key-value storage
   ↑
PersistQueryClientProvider — connects the persister to the query cache
```

The wiring is in `src/app/_queryClient.ts`, the provider is mounted in `src/app/App.tsx`. What physically lies in IndexedDB is one key with a serialized snapshot of the whole query cache, not a table of products or recipes. (The demo build swaps the persister for a no-op one, so a returning visitor never restores a snapshot that points at rows the nightly reset has removed.)

### What happens on start

1. `PersistQueryClientProvider` reads the snapshot from IndexedDB and restores the cache before the first render.
2. The screen shows the data from the last visit at once, with no spinner, even on a slow network.
3. In parallel, requests go to the database. When the answers arrive, the cache is updated and the screen re-renders.
4. The updated cache is written back to IndexedDB.

This is stale-while-revalidate: show the old data first, update quietly afterwards.

### How long the cache lives

`gcTime` and the persister `maxAge` are both 7 days (`CACHE_MAX_AGE` in `src/constants/caching.constants.ts`) instead of the default five minutes. The users live where international connectivity degrades for days ([ADR 0005](decisions/0005-tanstack-query-persisted-cache.md)): a five-minute cache is useless then, a week-long one is not. `CACHE_BUSTER` in the same file is the version of the persisted *shape*: when an entity that is stored in the cache changes shape, it is raised and old snapshots are discarded instead of breaking the screen on a missing field.

### What the cache does not do

- **It is a cache, not the source of truth.** The database wins on any difference. No data lives only in the cache.
- **Writing offline does not work.** A mutation without a network fails with an error. This is deliberate ([ADR 0005](decisions/0005-tanstack-query-persisted-cache.md)): a queue of deferred mutations is real work, and whether it is needed will show in practice. The recipe draft is saved to `localStorage` regardless of the network; that is a separate mechanism, unrelated to the query cache.
- **The browser may evict the storage**, when space runs low or the site data is cleared. The real backup is the JSON export in the settings, not IndexedDB.

## PWA

Three things make the app a PWA, and all three are in place:

1. **HTTPS**, provided by the hosting.
2. **A manifest**: the `manifest` section of `vite.config.ts` has the name, icons, colors and `display: "standalone"`. Because of it the phone offers "Add to Home Screen", and the launched app opens without the address bar.
3. **A service worker**, generated by `vite-plugin-pwa` at build time. It serves the precached files without touching the network.

### What is precached

At build time Workbox puts the build output into Cache Storage: HTML, JS, CSS and icons, the "app shell". That is why the app opens offline.

**Requests to Supabase are not cached by the service worker.** Data is the job of IndexedDB, and the two mechanisms are not mixed.

**The dictionaries (`public/dictionaries/*.json`) are part of the shell.** They are listed in `includeAssets` in `vite.config.ts`, and this protects against a specific failure. The default Workbox patterns precache only `js`, `css` and `html`, so the JSON would bypass the service worker and the browser would cache it heuristically: without `Cache-Control` a file counts as fresh for roughly 10% of its age, so a month-old file stays in the cache for days. The code, however, updates at once, because its file names carry a hash. A new component then asks for a key that the old dictionary does not have yet, and the screen fails.

A precached file gets a `revision` (a content hash) and arrives in the same transaction as the new JS, so the two cannot drift apart. The rule is general: **a `public/` file that the app fetches and that must match the code version goes into `includeAssets`.**

### How updates arrive

`registerType` is `autoUpdate`:

1. The app is opened and the old service worker serves the old version, which already runs.
2. A new build is downloaded in the background.
3. **It is applied on the next launch.**

So changes are not visible right after a deploy. To be sure, close the app from the list of running apps and open it again. This is the price of the instant start: to show the interface without waiting for the network, the service worker serves what it already has.

### First visit, repeat visit, offline

| | What happens |
|---|---|
| **First visit** | the network delivers the code, the service worker installs and fills Cache Storage; the data is loaded from the database |
| **Repeat visit** | the code comes from Cache Storage and the data from IndexedDB, both instantly; both are refreshed in the background |
| **Offline** | the code from Cache Storage, the data from IndexedDB. The app opens and shows everything that was there. Saving is impossible |
| **First visit offline** | nothing. There is nothing to cache |

### Why SPA + PWA, not SSR

The app is behind a login, so search engines have nothing to index. There is no server of our own, and adding one just for rendering would give up the whole architecture. Reading offline in the kitchen is a real need, and a PWA provides it. The reasoning is in [ADR 0003](decisions/0003-spa-pwa-on-vite.md).

## The data path

### Layers

```
page (src/pages/**)
   ↓ query hook
src/api/queries/**        ← TanStack Query: cache, invalidation, persistence
   ↓ function call
src/api/services/**       ← the only place that knows about PostgREST
   ↓ supabase-js
PostgREST → PostgreSQL (RLS)
```

Mutations live next to the queries in `src/api/mutations/**` and call the same services. A page never talks to Supabase directly; the rule is in [`agents/conventions/data.md`](agents/conventions/data.md).

### Why the service layer exists

A service **maps a database row to an app entity**. The database returns `active_variant_id`, `kcal_100`, `created_at`, the shape of the table. The app works with `activeVariantId`, `kcal100` and `createdAt`; the snake_case names never leave the service. The mapping is done here, once. Columns of type `numeric` arrive from PostgREST as `number`, so no conversion is needed.

This is not cosmetic. The nutrition module accepts `INutritionProduct` and `INutritionVariant`, contracts in camelCase written so that an entity fits them structurally, without an adapter. Keep the table shape, and an adapter would have to be written at every call site.

### How many requests go out

The whole dataset is loaded **in five requests**: product categories, dish categories, products with their variants, recipes with their ingredients, steps and category links, and the cook log. Search, filters and calculations then work on the data in memory. What matters is not the number but that it is **constant**: it does not grow with the number of open screens or with what is searched.

This looks wasteful and is not: the database stays at a few megabytes even after years. In return, search is instant and works offline, and no server-side search endpoints are needed. The decision and its reasons are in [ADR 0012](decisions/0012-whole-dataset-in-client.md). PostgREST returns related rows in one request, for example `select("*, product_variants!product_id (*)")` returns products together with their variants, which is why it is five requests and not twenty.

### Scenario: open the recipe list

1. The page calls `useRecipesQuery()`.
2. The cache already has data from the last visit (restored from IndexedDB), so **the list is drawn at once**.
3. In parallel the request goes out. RLS checks that the user is signed in.
4. The answer arrives and the service maps the rows to the app entities.
5. The cache is updated, the screen re-renders, and the snapshot goes to IndexedDB.
6. Search and filters work on the in-memory array, with no request at all.

### Scenario: add a product

1. The form calls a mutation hook.
2. The hook calls the service function `createProductWithVariant`, which calls the database function `create_product_with_variant` through `rpc`.
3. A product and its first variant are created **in one transaction** inside that function. The schema needs it: a composite foreign key forbids making another product's variant the active one, so the product is inserted first with an empty `active_variant_id`, then the variant, then the link is set. Doing this as three client requests could leave a half-created product behind ([ADR 0023](decisions/0023-rpc-for-multi-step-writes.md)).
4. On success the `products` key is invalidated, the query re-fetches, and the cache and IndexedDB are updated.
5. Every screen that shows products updates by itself. No manual reload.

### Scenario: calculate a recipe's nutrition

The calculation **does not touch the database at all**. `src/domain/nutrition/` holds pure functions over data that is already in memory:

1. For every ingredient, the pinned variant is taken if there is one, otherwise the product's active variant.
2. `nutrition per 100 g × grams / 100` is summed. Optional ingredients take part neither in the nutrition nor in the raw weight.
3. The divisor for "per 100 g" is the weight of the finished dish if it is set; otherwise it is the raw weight, and the interface warns that cooking loss is not accounted for.
4. A product with no nutrition filled in contributes zero **but is added to the list of incomplete products**, and the card shows a warning. There must be no silent zeros: wrong numbers are worse than missing ones.

The module imports neither React nor Supabase nor Mantine ([ADR 0017](decisions/0017-nutrition-module-purity.md)), so it runs in Node without a browser and is covered by tests independently of any interface.

**Why changing a product's active variant recalculates every recipe:** a recipe stores a reference to the product, not to a variant, and the active variant is a single field of the product. Change it, and every calculation that goes through that product gives a different result. There are no copies, so there is nothing to synchronize.

**The cook log does not change when that happens:** every entry stores a nutrition snapshot taken at the time of cooking, so the history is not rewritten after the fact ([ADR 0018](decisions/0018-cook-log-snapshot-and-dates.md)).
