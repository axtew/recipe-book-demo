# Как устроено приложение

---

## Часть 1. Общая картина

### Из чего состоит система

```
телефон / браузер                    интернет              Supabase (Сингапур)
┌────────────────────────┐                        ┌──────────────────────────┐
│ Приложение (React)     │                        │ GoTrue      — логин      │
│   ↕                    │                        │ PostgREST   — API к БД   │
│ Кэш в памяти           │◄──── HTTPS ───────────►│ Storage     — фото       │
│   ↕                    │                        │ PostgreSQL  — данные+RLS │
│ IndexedDB — кэш на диск│                        └──────────────────────────┘
│ Cache Storage — сам код│
└────────────────────────┘
```

Серверного кода у нас нет. Клиент обращается к Supabase напрямую, а роль «бэкенда» играет сам PostgreSQL: он проверяет права (RLS) и следит за целостностью (внешние ключи, ограничения). Подробнее почему так — `decisions.md §3`.

### Два разных хранилища в браузере — это главное, что путает

У приложения **две** независимые кладовки, и они хранят совершенно разное:

| | **Cache Storage** | **IndexedDB** |
|---|---|---|
| Что лежит | сам код приложения: JS, CSS, HTML, иконки | данные: продукты, рецепты, журнал |
| Кто пишет | service worker (PWA) | TanStack Query через персистер |
| Зачем | чтобы приложение **открылось** без сети | чтобы в нём **были данные** без сети |
| Обновляется | при выкатке новой версии | при каждом успешном запросе к базе |

Обе видны в DevTools → Application. Если приложение офлайн открывается, но пустое — работает Cache Storage, не работает IndexedDB. Если не открывается вовсе — наоборот.

## Часть 2. IndexedDB и кэш данных

### Что такое IndexedDB

Встроенная в браузер база данных. Не SQL: хранит объекты по ключам, как большой словарь. Три отличия от привычного `localStorage`:

| | localStorage | IndexedDB |
|---|---|---|
| Объём | ~5 МБ | сотни мегабайт и больше, зависит от свободного места |
| Тип данных | только строки | объекты, массивы, файлы, картинки |
| Доступ | синхронный — **блокирует отрисовку** | асинхронный |

Последнее важнее, чем кажется: чтение мегабайта из `localStorage` подвешивает интерфейс на это время. IndexedDB не подвешивает.

### Как мы её используем

Напрямую — никак. Цепочка из трёх слоёв, каждый следующий прячет предыдущий:

```
IndexedDB (браузер)
   ↑
idb-keyval — тонкая обёртка, даёт get / set / del
   ↑
@tanstack/query-async-storage-persister — умеет писать кэш в любое key-value хранилище
   ↑
PersistQueryClientProvider — подключает персистер к кэшу запросов
```

В коде это `src/app/_queryClient.ts`: там объявлен адаптер `idbStorage` с тремя методами, и он отдаётся персистеру. Всё.

**Что физически лежит в IndexedDB:** один ключ, в нём сериализованный слепок всего кэша запросов. Не таблица продуктов и не таблица рецептов — один блоб. Разбирать его руками не нужно и не предполагается.

### Что происходит при запуске приложения

1. `PersistQueryClientProvider` читает слепок из IndexedDB и восстанавливает кэш **до** первого рендера.
2. Экран сразу показывает данные с прошлого раза — без спиннера, даже если сеть медленная.
3. Параллельно уходит запрос к базе. Пришёл ответ — кэш обновился, экран перерисовался.
4. Обновлённый кэш пишется обратно в IndexedDB.

Это называется stale-while-revalidate: **сначала показать старое, потом тихо обновить**. Пользователь не ждёт сеть, чтобы увидеть свои рецепты.

### Сколько живёт кэш

В `_queryClient.ts` стоит `gcTime: 7 дней` вместо дефолтных пяти минут. Причина записана прямо там: во Вьетнаме рвутся подводные кабели, и международный трафик деградирует на дни (`decisions.md §3`). Кэш на пять минут в такой ситуации бесполезен, на неделю — спасает.

### Чего кэш не делает

**Это кэш, а не источник истины.** При расхождении выигрывает база. Кэш нужен для скорости и для чтения офлайн, но никакие данные не живут только в нём.

**Запись офлайн не работает.** Мутация без сети упадёт с ошибкой. Это осознанное решение (`decisions.md §3`): очередь отложенных мутаций — заметная работа, а понадобится ли она, выяснится на практике. Черновик рецепта при этом сохраняется в `localStorage` независимо от сети — отдельный механизм, к кэшу отношения не имеющий.

**Браузер может очистить хранилище.** При нехватке места, при очистке данных сайта. Для приложения, добавленного на домашний экран, iOS относится к данным бережнее, чем к обычной вкладке, но гарантий нет ни у кого. Поэтому настоящий бэкап — JSON-экспорт из настроек, а не надежда на IndexedDB.

### Как посмотреть своими глазами

DevTools → **Application**:

- **IndexedDB** → `keyval-store` → увидишь один ключ со слепком кэша;
- **Storage** → сколько занято;
- очистить всё — кнопка «Clear site data», приложение начнёт с чистого листа.

## Часть 3. PWA

### Что делает приложение «прогрессивным»

Три вещи, и все три у нас уже есть:

1. **HTTPS** — даёт Cloudflare Pages.
2. **Манифест** — `vite.config.ts`, секция `manifest`: имя, иконки, `display: "standalone"`, цвета. Из-за него телефон предлагает «добавить на экран Домой», а запущенное приложение открывается **без адресной строки**, как обычное.
3. **Service worker** — генерируется `vite-plugin-pwa` на сборке.

### Что такое service worker

Скрипт, который живёт **рядом со страницей, а не внутри неё**. У него нет доступа к DOM, зато он видит все сетевые запросы вкладки и может отвечать на них сам, не ходя в сеть.

Работает так:

```
страница просит /assets/index-abc123.js
        ↓
service worker: «этот файл у меня в Cache Storage»
        ↓
отдаёт из кэша — сеть не задействована вообще
```

При сборке Workbox складывает в Cache Storage весь результат сборки — то, что в логе сборки называется `precache 14 entries (800 KiB)`. Это «оболочка приложения»: HTML, JS, CSS, иконки. Поэтому приложение открывается офлайн — его код уже на устройстве.

**Запросы к Supabase service worker не кэширует.** Данные — забота IndexedDB, и смешивать эти два механизма не нужно.

**Словарь `public/dictionaries/ru.json` в оболочку входит** — он перечислен в `includeAssets` в `vite.config.ts`. Это не украшение, а защита от конкретной поломки. Дефолтные настройки Workbox складывают в precache только `js`, `css` и `html`; `json` прошёл бы мимо service worker'а и кэшировался браузером **эвристически** — без `Cache-Control` браузер считает файл свежим примерно 10% от его возраста, то есть месячный файл держит в кэше несколько дней. А код при этом обновляется сразу, потому что у него хеш в имени. Дальше новый компонент просит ключ, которого в старом словаре ещё нет, и экран падает.

Попав в precache, словарь получает `revision` — хеш содержимого — и приезжает **той же транзакцией**, что и новый JS. Разъехаться они уже не могут. Правило общее: любой файл из `public/`, который приложение читает `fetch`'ем и который обязан совпадать по версии с кодом, дописывается в `includeAssets`.

### Как приходят обновления

У нас `registerType: "autoUpdate"`. Что происходит:

1. Открыл приложение — старый service worker отдал старую версию, она уже работает.
2. Фоном скачалась новая сборка.
3. **Применится при следующем открытии.**

Отсюда правило: после выкатки изменения видны не сразу. Хочешь наверняка — закрой приложение из списка запущенных и открой заново. Это не баг, это цена мгновенного старта: чтобы отдать интерфейс без ожидания сети, service worker отдаёт то, что у него уже есть.

### Первый заход, повторный, офлайн

| | Что происходит |
|---|---|
| **Первый заход** | сеть тянет код, service worker устанавливается и кладёт всё в Cache Storage; данные грузятся из базы |
| **Повторный** | код из Cache Storage — мгновенно; данные из IndexedDB — мгновенно; фоном обновление обоих |
| **Офлайн** | код из Cache Storage, данные из IndexedDB. Приложение открывается и показывает всё, что было. Сохранить нельзя |
| **Первый заход офлайн** | ничего. Кэшировать нечего |

### PWA, SPA и SSR — это про разное

Частая путаница: их сравнивают как альтернативы, а они лежат на разных осях.

**SPA (Single Page Application)** — про то, где рисуется интерфейс. Сервер отдаёт один почти пустой HTML, дальше всё делает JavaScript в браузере, переходы между экранами без перезагрузки. **Наше приложение — SPA.**

**SSR (Server-Side Rendering)** — про то же самое, но HTML собирает сервер на каждый запрос. Нужен работающий сервер. Даёт индексацию поисковиками и более быстрый первый показ на слабых устройствах.

**PWA** — не про рендеринг вообще. Это набор возможностей поверх любого из двух: установка на домашний экран, работа офлайн, запуск без браузерной обвязки. PWA бывает и на SPA, и на SSR.

| | SPA | SSR | PWA |
|---|---|---|---|
| Где собирается HTML | в браузере | на сервере | не про это |
| Нужен сервер | нет | да | нет |
| Работает офлайн | нет сам по себе | нет | **да** |
| Индексируется поисковиками | плохо | хорошо | не про это |
| Ставится на домашний экран | нет | нет | **да** |

**Почему у нас SPA + PWA, а не SSR:** приложение за логином, поисковикам там делать нечего; своего сервера нет и заводить его ради рендеринга значило бы отказаться от всей архитектуры; а офлайн-чтение на кухне — реальная потребность, и его даёт именно PWA. Обоснование в `decisions.md §2`.

### Что смотреть в DevTools

**Application → Service Workers** — установлен ли, какая версия активна, кнопка `Update`.
**Application → Cache Storage** — что именно закэшировано.
**Network** — у запросов, отданных service worker'ом, в колонке `Size` написано `(ServiceWorker)` вместо размера.

Флажок **Offline** в Network — самый быстрый способ проверить, что офлайн действительно работает.

## Часть 4. Путь данных

> **Что из этого уже существует.** Раздел описывает целевую архитектуру целиком, а не текущее содержимое репозитория. На сегодня из перечисленного есть только клиент Supabase (`src/api/supabase.ts`) и экраны. Слой репозиториев появится в шаге `B6`, слой хуков — в Фазе 5, модуль расчёта — в Фазе 4. Пути ниже, которых пока нет в дереве, — не следы переименований, а места, куда код приедет.

### Слои и правило, которое их держит

```
экран (src/pages/**)
   ↓ хук запроса
src/api/queries/**        ← TanStack Query: кэш, инвалидация, персистентность
   ↓ вызов функции
src/api/repositories/**   ← единственное место, знающее про PostgREST
   ↓ supabase-js
PostgREST → PostgreSQL (RLS)
```

**Экран никогда не обращается к Supabase напрямую.** Ни «по-быстрому», ни в `useEffect`. `supabase.from(...)` вне `src/api/repositories/` — дефект. Причина не в чистоте: репозиторий это ещё и граница типов, и место, где чинится следующая ловушка.

### Строки вместо чисел — ловушка на границе

PostgREST отдаёт колонки типа `numeric` **строками**: `"120.50"`, а не `120.5`. Так сделано специально, чтобы не потерять точность по дороге — у JavaScript один числовой тип, и он двоичный.

Значит репозиторий обязан привести их к числам. Забыть — получить `"120" + 30 = "12030"` внутри расчёта КБЖУ, причём молча: сложение строк ошибки не даёт.

За границей репозитория строкочисел быть не должно.

### Сколько запросов уходит

Весь датасет грузится **целиком, четырьмя запросами**: категории, продукты с вариантами, рецепты с ингредиентами и шагами, журнал. Дальше поиск, фильтры и расчёты идут по данным в памяти.

Это выглядит расточительно и таковым не является: база — единицы мегабайт даже через годы. Зато поиск мгновенный и работает офлайн, а серверных endpoint'ов поиска не нужно вовсе. Решение и его обоснование — `decisions.md §3`.

PostgREST умеет отдавать связанные данные одним запросом: `select("*, product_variants(*)")` вернёт продукты вместе с вариантами. Поэтому четыре запроса, а не двадцать.

### Сценарий: открыть список рецептов

1. Экран вызывает `useRecipesQuery()`.
2. В кэше есть данные с прошлого раза (восстановлены из IndexedDB) — **список рисуется сразу**.
3. Параллельно уходит запрос. RLS проверяет, что пользователь залогинен.
4. Ответ пришёл, репозиторий превратил строки в числа и разложил в доменные типы.
5. Кэш обновился → экран перерисовался → слепок ушёл в IndexedDB.
6. Поиск и фильтры работают по массиву в памяти, без единого запроса.

### Сценарий: добавить продукт

1. Форма вызывает хук мутации.
2. Тот зовёт функцию репозитория, она делает `insert`.
3. Тонкость схемы: продукт и его первый вариант создаются **тремя шагами** — продукт с пустым `active_variant_id`, затем вариант, затем простановка ссылки. Так требует составной внешний ключ, который не даёт назначить активным вариант чужого продукта (`plans/recipe-book-v1/phase-1-tutorial.md`, §3.3).
4. Успех → инвалидация ключа `products` → перезапрос → кэш и IndexedDB обновились.
5. Все экраны, показывающие продукты, обновились сами. Ручных перезагрузок нет.

### Сценарий: посчитать КБЖУ рецепта

Расчёт **не ходит в базу вообще**. `src/domain/nutrition/` — чистые функции над данными, которые уже в памяти:

1. Для каждого ингредиента берётся закреплённый вариант, если задан, иначе активный вариант продукта.
2. Суммируются `кбжу_на_100 × граммы / 100`. Опциональные ингредиенты не участвуют — ни в КБЖУ, ни в весе сырья.
3. Делитель для «на 100 г» — вес готового блюда, если задан; иначе вес сырья, и интерфейс честно предупреждает, что уварка не учтена.
4. Продукт без заполненного КБЖУ даёт вклад ноль, **но попадает в список проблемных**, и карточка показывает предупреждение. Молчаливых нулей быть не должно: неверные цифры хуже отсутствующих.

Модуль не импортирует ни React, ни Supabase, ни Mantine — он должен запускаться в Node без браузера. Поэтому его можно покрыть тестами до всякого интерфейса и переиспользовать на сервере, если однажды понадобится.

**Почему смена марки продукта пересчитывает все рецепты:** рецепт хранит ссылку на продукт, а не на вариант. Активный вариант — одно поле у продукта. Поменял его — все расчёты, которые идут через этот продукт, дали другой результат. Копий нигде нет, синхронизировать нечего.

**А журнал готовки при этом не меняется:** каждая запись хранит снапшот КБЖУ на момент готовки. История не переписывается задним числом.
