# i18n

## Все локали, всегда

Весь видимый пользователю текст (подписи, плейсхолдеры, подсказки, сообщения об ошибках, пустые состояния) идёт через систему i18n и никогда не хардкодится в JSX. Любой видимый пользователю ключ, который вы добавляете, попадает **во все** словари в папке словарей одновременно — в каждую локаль, существующую сейчас и добавленную позже (не хардкодьте список — перечислите папку). Каждый файл получает значение, переведённое на **язык, который этот файл представляет** (`en.json` → английский, `kg.json` → киргизский, `ru.json` → русский и т. д.). Добавление ключа лишь в часть словарей ломает переключение локали и является дефектом.

**Ключи словаря — это идентификаторы, а не данные.** Ключ должен соответствовать `^[A-Za-z0-9_]+$` — только латинские буквы, цифры и `_`. Без кириллицы, пробелов, знаков препинания, разделителей вроде `;` или `/`. Обычные ключи остаются `camelCase`, как и остальной словарь; ключи, обозначающие значения enum, пишутся `UPPER_SNAKE_CASE` и совпадают с членом enum, которому соответствуют.

Сбой, который предотвращает это правило: сырое значение поставщика вставляют в качестве ключа, получая записи вроде `"GSM; microwave; television"` или `"муниципальная"`. Такой ключ становится частью публичного типа `I18n`, недоступен через точку и молча ломается, как только источник данных переформулирует значение. Если значение выглядит непригодным для ключа, это сигнал, что **данным** нужен код — исправляйте выше по потоку, а не кодируйте здесь сырую строку. Значение, несущее несколько сущностей через `;`, — это список, и в данных ему место массивом кодов, а не одним составным ключом.

**Типизируйте словарь значений через его enum.** Когда у ограниченного набора значений есть enum, словарь типизируется `Record<EEnumName, string>`. Когда enum нет, объявите обычный объектный тип с явными ключами. Никогда не типизируйте его как `Record<"literal" | "another", string>` — union строковых литералов выглядит проверяемым типом, но на деле фиксирует точное написание источника, так что переформулированное значение упадёт в рантайме, а не при компиляции. Это зеркало правила о словарях, типизируемых через enum, из [`typing.md`](typing.md): `Record` с ключами из enum — умолчание, когда enum существует.

**`useI18nSelector` выбирает узкий срез.** Селектор возвращает конкретную ветку (или объект, составленный из нескольких конкретных веток), которая компоненту действительно нужна, — но никогда не корневой `l`. Возврат всего словаря подписывает компонент на любое изменение переводов и скрывает, от какой части словаря он на самом деле зависит. Забраться в `l`, а потом сужать в теле компонента — та же ошибка, написанная иначе.

**Один `l` на компонент, и аргумент селектора всегда `({ l })`.** Результат селектора привязывается к единственной `const l`; чтения выглядят как `l.caloriesLabel`, а не `card.caloriesLabel`. Строится он распространением собственной основной ветки компонента и подключением нужных дополнительных веток именованными ключами:

```ts
const l = useI18nSelector(({ l }) => ({
  ...l.recipePage.card,
  units: l.common.units,
}));
```

Компонент без основной ветки (общий фрагмент) пропускает распространение и оставляет только именованные ключи. Два вида — дефекты: переименование аргумента селектора (`({ l: localization }) => …`) и деструктуризация результата в несколько имён (`const { l, units } = …`). Оба ломают единственную конвенцию, благодаря которой чтения i18n ищутся grep'ом, — `l` это срез словаря везде.

**`src/types/i18n.types.ts` экспортирует ровно одну вещь — интерфейс `I18n`.** Этот файл — форма словарей и ничего больше. Вспомогательные типы, которые случайно используются *внутри* него (союзы ключей, алиасы enum, всё, по чему ключуется ветка словаря), объявляются в доменном файле, которому принадлежит понятие (типы сущностей — в `src/types/<domain>.types.ts`), и импортируются сюда. Объявление их в `i18n.types.ts` переворачивает зависимость: потребители начинают импортировать доменный словарь из файла переводов, а понятие оказывается во владении того слоя, которому первому понадобился ключ словаря. Правила размещения типов из [`structure.md`](structure.md) действуют без изменений; это лишь напоминание, что файл словарей никогда не бывает коротким путём для типа.

## Особенности проекта

Словари лежат в `public/dictionaries/`, по одному файлу на локаль. Сейчас он ровно один — `ru.json`, и интерфейс только русский; инфраструктура существует, чтобы видимые пользователю тексты с самого начала собирались в одном месте, а не вытаскивались из JSX позже. Все правила раздела выше применяются к этому единственному словарю без изменений ([ADR 0002](../../decisions/0002-russian-ui-with-i18n.md)).

Интерфейс `I18n` — это `src/types/i18n.types.ts`; хук-селектор — `useI18nSelector` из `src/context/I18nContext`.

**Видимый пользователю текст не привязан к полу.** Приложением пользуются двое людей разного пола, поэтому русский текст никогда не обращается к пользователю и не описывает его в роде прошедшего времени («готовила», «добавил»). Используйте безличную или страдательную форму («Пока ни разу не готовилось», «Приготовлено раз»), множественное число («Готовили», «доели») или существительное / инфинитив в подписи («Записать готовку»). Исходное ТЗ [`docs/task.md`](../../task.md) написано в женском роде — не переносите его формулировки в словарь.
