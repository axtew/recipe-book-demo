# i18n

## Every locale, always

All user-visible text (labels, placeholders, hints, error messages, empty states) goes through the i18n system, never hardcoded in JSX. Any user-visible key you add goes into **every** dictionary in the dictionaries folder simultaneously — every locale present now and any added later (don't hardcode the list — enumerate the folder). Each file gets the value translated into **the language that file represents** (`en.json` → English, `ru.json` → Russian, and so on). Adding a key to only some dictionaries breaks the locale switch and is a defect.

**Dictionary keys are identifiers, not data.** A key must match `^[A-Za-z0-9_]+$` — Latin letters, digits and `_` only. No Cyrillic, no spaces, no punctuation, no separators like `;` or `/`. Ordinary keys stay `camelCase` like the rest of the dictionary; keys that stand for enum values are `UPPER_SNAKE_CASE` and identical to the enum member they map to.

The failure mode this rule prevents: a raw supplier value gets pasted in as a key, producing entries like `"GSM; microwave; television"` or a key written in a non-Latin script. That key is now part of the public `I18n` type, it is unreachable via dot access, and it silently breaks the moment the data source rewords the value. If a value looks unfit to be a key, that is a signal the **data** needs a code — fix it upstream instead of encoding the raw string here. A value carrying several entities separated by `;` is a list, and belongs in the data as an array of codes, not as one composite key.

**Type a value dictionary through its enum.** When a bounded set of values has an enum, the dictionary is typed `Record<EEnumName, string>`. When there is no enum, declare a plain object type with explicit keys. Never type it as `Record<"literal" | "another", string>` — a union of string literals looks like a checked type but actually pins the source's exact spelling, so a reworded value fails at runtime instead of at compile time. This mirrors the rule about enum-typed maps in [`typing.md`](typing.md): an enum-keyed `Record` is the default whenever an enum exists.

**`useI18nSelector` selects a narrow slice.** The selector returns the specific branch (or an object composed of a few specific branches) that the component actually needs — never the root `l`. Returning the whole dictionary subscribes the component to every translation change and hides which part of the dictionary it truly depends on. Reaching into `l` and then narrowing in the component body is the same mistake written differently.

**One `l` per component, and the selector argument is always `({ l })`.** The selector's result is bound to a single `const l`; reads look like `l.caloriesLabel`, never `card.caloriesLabel`. Build it by spreading the component's own primary branch and attaching the extra branches it needs as named keys:

```ts
const l = useI18nSelector(({ l }) => ({
  ...l.recipePage.card,
  units: l.common.units,
}));
```

A component with no primary branch (a shared fragment) skips the spread and keeps only named keys. Two shapes are defects: renaming the selector argument (`({ l: localization }) => …`) and destructuring the result into several names (`const { l, units } = …`). Both break the one convention that makes i18n reads greppable — `l` is the dictionary slice, everywhere.

**`src/types/i18n.types.ts` exports exactly one thing — the `I18n` interface.** That file is the shape of the dictionaries and nothing else. Helper types that happen to be used *inside* it — key unions, enum aliases, anything a dictionary branch is keyed by — are declared in the domain file that owns the concept (entity types in `src/types/<domain>.types.ts`) and imported here. Declaring them in `i18n.types.ts` inverts the dependency: consumers start importing domain vocabulary from the translations file, and the concept ends up owned by whichever layer first needed a dictionary key. The type placement rules from [`structure.md`](structure.md) apply unchanged; this is only the reminder that the dictionary file is never a shortcut home for a type.

## Project specifics

Dictionaries live in `public/dictionaries/`, one file per language: `en.json` and `ru.json` ([ADR 0034](../../decisions/0034-bilingual-ui-by-browser-language.md)). The `I18n` interface in `src/types/i18n.types.ts` is the shape of both, and every rule above applies to each dictionary: a key exists in both, or the change is not done. The key-parity test (`src/context/I18nContext/__tests__/dictionaries.test.ts`) enumerates the folder, compares the key set of every file with `ru.json` and checks that every leaf is a non-empty string; it fails on a key missing from one dictionary.

- **Language detection and storage.** `detectLanguage` (`src/context/I18nContext/_language.ts`) picks the language: a stored choice wins, otherwise a browser whose primary language starts with `ru` gets Russian and everything else gets English. An explicit choice is made only in the settings and is written to `localStorage` (`LANGUAGE_STORAGE_KEY`); detection never writes to storage.
- **Access from React.** The selector hook is `useI18nSelector` from `src/context/I18nContext`; the current language and its setter come from `useLanguage()` in the same place. Code outside React reads the dictionary with `getDictionary()`.
- **Display formats follow the language.** Numbers and dates are formatted by the helpers in `src/utils/helpers/` (`nutrients.ts`, `dates.ts`), which read the display language through `src/utils/helpers/locale.ts`. The provider sets that value together with the dictionary, so a render never mixes labels of one language with formats of another. English: `1,234.5`, `25 Oct 2026`, the week starts on Monday; Russian: `1 234,5`, `DD.MM.YYYY`. A new formatter reads the language from `locale.ts` and does not take it as an argument.

**User-visible Russian text is gender-neutral.** The app is used by two people of different genders, so Russian copy never addresses or describes the user in a gendered past tense (the feminine or masculine past-tense verb for "cooked" or "added"). Use an impersonal or passive form (for "not cooked yet" and "cooked N times", the impersonal and passive wordings already in `ru.json`), the plural ("they cooked", "they finished"), or a noun / infinitive label (for "log a cook", the infinitive wording). Look at the neighbouring entries of `ru.json` and match them. The original spec [`docs/task.md`](../../task.md) is written in the feminine — do not copy its wording into the dictionary. The rule is about the Russian text; English copy has no gendered forms and addresses the user neutrally too.

**English style.** Sentence case for buttons and titles; neutral, impersonal tone, like `ru.json`; every `{placeholder}` is kept verbatim; a "label: count" string is a label without a number. Guillemets (« ») used in Russian text become plain double quotes in English text. Use one English term per concept, the one the dictionary already uses:

| Concept | English term |
|---|---|
| a product, the product list | product, product list |
| a product variant, the one in use | variant, active |
| the four nutrition values | nutrition; kcal, P / F / C (protein, fat, carbs) |
| weight | grams, g |
| recipe parts | recipe, ingredient, step |
| a portion; the weight of the cooked dish | serving; yield (cooked weight) |
| the cooking log and its entries | log (cooking log), cook, log a cook |
| a product that is used up | finished |
| hiding without deleting | archive, archived |
| storage places | storage, freezer, fridge |
| a dish category | dish category |
| an unsaved recipe | draft |
| data transfer | backup, export, import |

Before inventing a term, search `en.json` for the concept and reuse what is there.
