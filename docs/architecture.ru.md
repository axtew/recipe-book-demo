# Архитектура

Как устроено приложение: откуда берутся данные на экране, что хранит браузер и как PWA работает без сети. Решения, на которых это построено, — в [`decisions/`](decisions/README.md).

## Общая схема

```
телефон / браузер                     интернет            Supabase (Сингапур)
┌────────────────────────┐                        ┌──────────────────────────┐
│ Приложение (React)     │                        │ GoTrue      — вход       │
│   ↕                    │                        │ PostgREST   — API к БД   │
│ Кэш запросов в памяти  │◄──── HTTPS ───────────►│ Storage     — фото       │
│   ↕                    │                        │ PostgreSQL  — данные+RLS │
│ IndexedDB — копия кэша │                        └──────────────────────────┘
│ Cache Storage — код    │
└────────────────────────┘
```

Собственного серверного кода нет. Клиент общается с Supabase напрямую, а роль бэкенда играет PostgreSQL: он следит за доступом (RLS) и целостностью (внешние ключи, ограничения). Причины — в [ADR 0010](decisions/0010-supabase-without-own-backend.md). Статические файлы раздаёт Cloudflare Workers Static Assets ([ADR 0013](decisions/0013-cloudflare-hosting.md)).

## Два хранилища браузера

Приложение использует два независимых хранилища, и лежит в них разное:

| | **Cache Storage** | **IndexedDB** |
|---|---|---|
| Что хранит | код приложения: JS, CSS, HTML, иконки, словари | данные: продукты, рецепты, журнал готовки |
| Кто пишет | сервис-воркер (PWA) | TanStack Query через персистер |
| Зачем | приложение **открывается** без сети | в приложении **есть данные** без сети |
| Когда обновляется | при выкатке новой версии | после каждого успешного запроса к базе |

Если приложение открывается без сети, но пустое, — работает Cache Storage, а IndexedDB нет. Если не открывается вообще — наоборот.

## Кэш данных

### Как кэш попадает в IndexedDB

Приложение никогда не обращается к IndexedDB напрямую. Цепочка такая:

```
IndexedDB
   ↑
idb-keyval — тонкая обёртка с get / set / del
   ↑
@tanstack/query-async-storage-persister — пишет кэш в любое хранилище «ключ — значение»
   ↑
PersistQueryClientProvider — подключает персистер к кэшу запросов
```

Подключение — в `src/app/_queryClient.ts`, провайдер монтируется в `src/app/App.tsx`. Физически в IndexedDB лежит один ключ с сериализованным снимком всего кэша запросов, а не таблица продуктов или рецептов. (Демо-сборка заменяет персистер пустым, чтобы вернувшийся посетитель не восстанавливал снимок со строками, которые ночной сброс уже убрал.)

### Что происходит при запуске

1. `PersistQueryClientProvider` читает снимок из IndexedDB и восстанавливает кэш до первого рендера.
2. Экран сразу показывает данные с прошлого визита, без спиннера, даже при медленной сети.
3. Параллельно к базе уходят запросы. Когда приходят ответы, кэш обновляется и экран перерисовывается.
4. Обновлённый кэш записывается обратно в IndexedDB.

Это stale-while-revalidate: сначала показать старые данные, потом тихо обновить.

### Сколько живёт кэш

`gcTime` и `maxAge` персистера равны 7 дням (`CACHE_MAX_AGE` в `src/constants/caching.constants.ts`) вместо пяти минут по умолчанию. Пользователи живут там, где международная связь по несколько дней ухудшается ([ADR 0005](decisions/0005-tanstack-query-persisted-cache.md)): кэш на пять минут тогда бесполезен, недельный — нет. `CACHE_BUSTER` в том же файле — версия сохранённой *формы*: когда меняется форма сущности, которая лежит в кэше, константа поднимается, и старые снимки отбрасываются, а не ломают экран отсутствующим полем.

### Чего кэш не делает

- **Он кэш, а не источник истины.** При любом расхождении побеждает база. Данных, которые живут только в кэше, нет.
- **Запись без сети не работает.** Мутация без сети падает с ошибкой. Это сделано осознанно ([ADR 0005](decisions/0005-tanstack-query-persisted-cache.md)): очередь отложенных мутаций — это настоящая работа, а нужна ли она, покажет практика. Черновик рецепта сохраняется в `localStorage` независимо от сети; это отдельный механизм, не связанный с кэшем запросов.
- **Браузер может выселить хранилище**, когда не хватает места или очищаются данные сайта. Настоящий бэкап — это JSON-экспорт в настройках, а не IndexedDB.

## PWA

Приложение становится PWA благодаря трём вещам, и все три на месте:

1. **HTTPS**, его даёт хостинг.
2. **Манифест**: раздел `manifest` в `vite.config.ts` содержит название, иконки, цвета и `display: "standalone"`. Благодаря ему телефон предлагает «На экран „Домой“», а запущенное приложение открывается без адресной строки.
3. **Сервис-воркер**, который `vite-plugin-pwa` генерирует при сборке. Он отдаёт закэшированные заранее файлы, не обращаясь к сети.

### Что кэшируется заранее

При сборке Workbox кладёт результат сборки в Cache Storage: HTML, JS, CSS и иконки — «оболочку» приложения. Поэтому приложение открывается без сети.

**Запросы к Supabase сервис-воркер не кэширует.** Данные — дело IndexedDB, и два механизма не смешиваются.

**Словари (`public/dictionaries/*.json`) — часть оболочки.** Они перечислены в `includeAssets` в `vite.config.ts`, и это защищает от конкретного сбоя. Шаблоны Workbox по умолчанию кэшируют заранее только `js`, `css` и `html`, поэтому JSON обошёл бы сервис-воркер, а браузер кэшировал бы его эвристически: без `Cache-Control` файл считается свежим примерно 10% своего возраста, так что месячный файл остаётся в кэше на несколько дней. Код же обновляется сразу, потому что в именах его файлов есть хеш. Тогда новый компонент запрашивает ключ, которого в старом словаре ещё нет, и экран ломается.

Заранее закэшированный файл получает `revision` (хеш содержимого) и приходит в той же транзакции, что и новый JS, так что разойтись они не могут. Правило общее: **файл из `public/`, который приложение запрашивает и который должен соответствовать версии кода, попадает в `includeAssets`.**

### Как приходят обновления

`registerType` равен `autoUpdate`:

1. Приложение открыто, старый сервис-воркер отдаёт старую версию, и она уже работает.
2. Новая сборка скачивается в фоне.
3. **Она применяется при следующем запуске.**

Поэтому изменения не видны сразу после выкатки. Чтобы убедиться, закройте приложение в списке запущенных и откройте снова. Это цена мгновенного старта: чтобы показать интерфейс, не дожидаясь сети, сервис-воркер отдаёт то, что у него уже есть.

### Первый визит, повторный, без сети

| | Что происходит |
|---|---|
| **Первый визит** | сеть доставляет код, сервис-воркер устанавливается и наполняет Cache Storage; данные загружаются из базы |
| **Повторный визит** | код приходит из Cache Storage, данные из IndexedDB, оба мгновенно; оба обновляются в фоне |
| **Без сети** | код из Cache Storage, данные из IndexedDB. Приложение открывается и показывает всё, что в нём было. Сохранить ничего нельзя |
| **Первый визит без сети** | ничего. Кэшировать нечего |

### Почему SPA + PWA, а не SSR

Приложение закрыто логином, поэтому поисковикам индексировать нечего. Собственного сервера нет, и добавлять его только ради рендеринга значило бы отказаться от всей архитектуры. Чтение без сети на кухне — реальная потребность, и PWA её закрывает. Обоснование — в [ADR 0003](decisions/0003-spa-pwa-on-vite.md).

## Путь данных

### Слои

```
страница (src/pages/**)
   ↓ query-хук
src/api/queries/**        ← TanStack Query: кэш, инвалидация, персистенция
   ↓ вызов функции
src/api/services/**       ← единственное место, которое знает про PostgREST
   ↓ supabase-js
PostgREST → PostgreSQL (RLS)
```

Мутации лежат рядом с запросами в `src/api/mutations/**` и вызывают те же сервисы. Страница никогда не обращается к Supabase напрямую; правило записано в [`agents/conventions/data.md`](agents/conventions/data.md).

### Зачем нужен слой сервисов

Сервис **превращает строку базы в сущность приложения**. База возвращает `active_variant_id`, `kcal_100`, `created_at` — форму таблицы. Приложение работает с `activeVariantId`, `kcal100` и `createdAt`; имена в snake_case за пределы сервиса не выходят. Преобразование делается здесь, один раз. Столбцы типа `numeric` приходят из PostgREST как `number`, так что преобразовывать их не нужно.

Это не косметика. Модуль расчёта принимает `INutritionProduct` и `INutritionVariant` — контракты в camelCase, написанные так, чтобы сущность подходила под них структурно, без адаптера. Оставь форму таблицы — и адаптер пришлось бы писать в каждом месте вызова.

### Сколько уходит запросов

Весь набор данных загружается **пятью запросами**: категории продуктов, категории блюд, продукты с вариантами, рецепты с ингредиентами, шагами и связями с категориями, журнал готовки. Дальше поиск, фильтры и расчёты работают по данным в памяти. Важно не число, а то, что оно **постоянное**: не растёт ни с числом открытых экранов, ни с тем, что ищут.

Это выглядит расточительно, но это не так: база остаётся в пределах нескольких мегабайт и через годы. Взамен поиск мгновенный и работает без сети, а серверные точки поиска не нужны. Решение и его причины — в [ADR 0012](decisions/0012-whole-dataset-in-client.md). PostgREST возвращает связанные строки одним запросом, например `select("*, product_variants!product_id (*)")` отдаёт продукты вместе с вариантами, поэтому запросов пять, а не двадцать.

### Сценарий: открыть список рецептов

1. Страница вызывает `useRecipesQuery()`.
2. В кэше уже есть данные с прошлого визита (восстановленные из IndexedDB), поэтому **список рисуется сразу**.
3. Параллельно уходит запрос. RLS проверяет, что пользователь вошёл.
4. Приходит ответ, и сервис превращает строки в сущности приложения.
5. Кэш обновляется, экран перерисовывается, а снимок уходит в IndexedDB.
6. Поиск и фильтры работают по массиву в памяти, вообще без запросов.

### Сценарий: добавить продукт

1. Форма вызывает хук мутации.
2. Хук вызывает функцию сервиса `createProductWithVariant`, а та через `rpc` вызывает функцию базы `create_product_with_variant`.
3. Продукт и его первый вариант создаются **в одной транзакции** внутри этой функции. Этого требует схема: составной внешний ключ не позволяет сделать активным вариант другого продукта, поэтому сначала вставляется продукт с пустым `active_variant_id`, затем вариант, затем проставляется связь. Если делать это тремя клиентскими запросами, мог бы остаться наполовину созданный продукт ([ADR 0023](decisions/0023-rpc-for-multi-step-writes.md)).
4. При успехе ключ `products` инвалидируется, запрос перечитывается, кэш и IndexedDB обновляются.
5. Каждый экран, показывающий продукты, обновляется сам. Перезагружать вручную не нужно.

### Сценарий: рассчитать КБЖУ рецепта

Расчёт **вообще не обращается к базе**. `src/domain/nutrition/` — чистые функции над данными, которые уже есть в памяти:

1. Для каждого ингредиента берётся закреплённый вариант, если он есть, иначе активный вариант продукта.
2. Суммируется `КБЖУ на 100 г × граммы / 100`. Необязательные ингредиенты не участвуют ни в КБЖУ, ни в весе сырья.
3. Делитель для «на 100 г» — вес готового блюда, если он задан; иначе вес сырья, и интерфейс предупреждает, что уварка не учтена.
4. Продукт без заполненного КБЖУ даёт ноль, **но попадает в список неполных продуктов**, и карточка показывает предупреждение. Молчаливых нулей быть не должно: неверные цифры хуже отсутствующих.

Модуль не импортирует ни React, ни Supabase, ни Mantine ([ADR 0017](decisions/0017-nutrition-module-purity.md)), поэтому работает в Node без браузера и покрыт тестами независимо от любого интерфейса.

**Почему смена активного варианта продукта пересчитывает каждый рецепт:** рецепт хранит ссылку на продукт, а не на вариант, и активный вариант — единственное поле продукта. Меняешь его — и каждый расчёт, проходящий через этот продукт, даёт другой результат. Копий нет, поэтому синхронизировать нечего.

**Журнал готовки при этом не меняется:** каждая запись хранит снимок КБЖУ на момент готовки, так что история не переписывается задним числом ([ADR 0018](decisions/0018-cook-log-snapshot-and-dates.md)).
