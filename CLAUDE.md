# Книга рецептов — инструкции проекта

Личное mobile-first приложение для двух человек: справочник продуктов, рецепты с расчётом КБЖУ, поиск, журнал готовки. Интерфейс на русском, единственный язык — i18n здесь не нужен.

## Обязательное чтение перед любой работой

1. **`decisions.md`** — журнал решений. Источник истины по стеку, модели данных и границам продукта. При расхождении с чем угодно приоритет у него.
2. **`plans/recipe-book-v1/plan.md`** — план реализации: схема БД, доменные типы, контракт модуля расчёта, карта экранов, фазы.
3. `recipe-app-v1-prompt.md` — исходное ТЗ. Историческая справка: часть его решений отменена в `decisions.md`, отменённое перечислено там же в §4.

Справочно, читать по необходимости:

- **`DEPLOY.md`** — деплой, переменные окружения, порядок работы с миграциями в проде, чек-лист релиза.
- **`BACKLOG.md`** — идеи по развитию и техдолг. Читать не обязательно, но **если в разговоре всплыла идея на будущее — записать туда**, а не потерять. Там же раздел «Отклонённое» с причинами: прежде чем предлагать что-то «полезное», проверить, не отклонено ли оно уже.

## Разделение работ — читать до начала

Всё, что касается базы данных и границы с ней, **выполняет владелец проекта вручную**. Это осознанное решение (он изучает предметную область), а не пробел в плане.

**Не создавать и не редактировать:**

- `supabase/**` — миграции, конфиг, seed
- `.env` — можно только `.env.example`
- `src/types/database.types.ts` — генерируется из схемы
- `src/api/repositories/**`

**Не выполнять целиком:** Фазу 1 (база данных) и часть Фазы 5 (репозитории). Кто что делает по фазам — таблица в `plans/recipe-book-v1/plan.md`, раздел «Кто что выполняет»; полный список работ владельца — `plans/recipe-book-v1/backend-track.md`.

**Если для фазы нужно изменение схемы** — не хватает столбца, мешает ограничение, нужен индекс — **остановиться и сообщить владельцу**. Не писать миграцию, не обходить стороной, не подставлять заглушку, не считать «потом поправим». Владелец пишет миграцию и перегенерирует типы, после этого работа продолжается.

**Если фаза упирается в незакрытый шаг бэкенд-трека** (нет `.env`, нет типов, нет репозиториев) — сказать об этом и остановиться, а не изобретать временное решение.

## Как выполнять фазу

Одна сессия — одна фаза. Протокол:

1. Прочитать `decisions.md` и раздел нужной фазы в плане целиком.
2. Делать **только эту фазу**. Файлы, не перечисленные в её списке, не трогать. Заметил нужную правку за пределами фазы — сказать об этом, а не делать молча.
3. В конце пройти по пунктам раздела **«Проверка»** этой фазы и отчитаться по каждому: выполнено или нет, с фактическим выводом команд. Не отчитываться об успехе там, где не проверял.
4. **Не коммитить.** Изменения остаются в рабочем дереве — их смотрит и коммитит владелец проекта.

Если план расходится с реальностью (не существует того, на что он ссылается; шаг противоречит другому решению; выясняется, что задумка не работает) — **остановиться и спросить**. Не изобретать обходной путь молча: план правится осознанно, через дополнение в разделе «Дополнения».

## Жёсткие инварианты

Нарушение любого из них — дефект, даже если код работает.

- **Вся арифметика КБЖУ живёт только в `src/domain/nutrition/`.** Ни один компонент, хук или репозиторий не считает питательность сам. Модуль не импортирует React, Supabase и Mantine — он должен запускаться в Node без DOM.
- **Удалений нет.** Только `archived_at`. Никаких `DELETE` из приложения ни по одной сущности.
- **Молчаливых нулей не бывает.** Продукт без КБЖУ даёт запись в `incompleteProducts` и видимое предупреждение в UI, а не ноль в сумме.
- **Округление только при отображении.** Домен возвращает сырые числа: ккал до целых и БЖУ до одного знака — работа UI.
- **`numeric` из PostgREST приходит строкой.** Приведение к `number` делает репозиторий на границе. Дальше по приложению строкочисел быть не должно.
- **Даты `cooked_at` / `finished_at`** — строки `YYYY-MM-DD`. Никаких `Date` и часовых поясов.
- **Приоритет у iOS.** Основной пользователь на iPhone. Расхождение поведения между платформами решается в пользу Safari на iOS. Только `100dvh`, `env(safe-area-inset-*)`, tap targets ≥44px.
- **Новые зависимости — только с разрешения.** Стек зафиксирован в `decisions.md §2`. Понадобилось что-то ещё — спросить.
- **Данные загружаются в клиент целиком.** Никаких серверных endpoint'ов поиска, никакой пагинации, никакой фильтрации на стороне БД. Поиск и фильтры — по датасету в памяти.

## Команды

Заполняются по мере появления (Фазы 1–2). Ожидаемый набор:

```
pnpm dev            # дев-сервер
pnpm build          # прод-сборка
pnpm lint           # линт
pnpm test           # vitest
pnpm db:reset       # пересоздать локальную БД из миграций + seed
pnpm db:types       # перегенерировать src/types/database.types.ts
```

После правки схемы БД **всегда** перегенерировать типы — руками `database.types.ts` не редактировать.

## Чего в проекте нет

Не предлагать и не добавлять по своей инициативе: SSR, серверный код помимо Supabase Edge Functions, мультипользовательность и роли, миллилитры и конверсии единиц, десктопный layout (одна колонка `max-width: 600px`), офлайн-запись. Обоснования — в `decisions.md`.
