# Книга рецептов — инструкции проекта

Личное mobile-first приложение для двух человек: справочник продуктов, рецепты с расчётом КБЖУ, поиск, журнал готовки. Интерфейс на русском, единственный язык — i18n здесь не нужен.

## Обязательное чтение перед любой работой

0. **`STATUS.md`** — где мы сейчас: закрытые фазы, следующий шаг, открытые вопросы. Начинать с него.
1. **`decisions.md`** — журнал решений. Источник истины по стеку, модели данных и границам продукта. При расхождении с чем угодно приоритет у него.
2. **`plans/recipe-book-v1/plan.md`** — план реализации: схема БД, доменные типы, контракт модуля расчёта, карта экранов, фазы.
3. `recipe-app-v1-prompt.md` — исходное ТЗ. Историческая справка: часть его решений отменена в `decisions.md`, отменённое перечислено там же в §4.

Справочно, читать по необходимости:

- **`DEPLOY.md`** — деплой, переменные окружения, порядок работы с миграциями в проде, чек-лист релиза.
- **`docs/how-it-works.md`** — как устроено приложение: путь данных, кэш в IndexedDB, PWA и service worker. Читать, если непонятно, откуда берутся данные на экране.
- **`BACKLOG.md`** — идеи по развитию и техдолг. Читать не обязательно, но **если в разговоре всплыла идея на будущее — записать туда**, а не потерять. Там же раздел «Отклонённое» с причинами: прежде чем предлагать что-то «полезное», проверить, не отклонено ли оно уже.

## Разделение работ — читать до начала

**С 2026-10-18 исполнители пишут всё, включая базу.** До этого слой данных — миграции, сервисы, хуки запросов, схемы zod — владелец писал руками, чтобы изучить предметную область. Обучение вынесено за пределы проекта, приоритет — запуск. История решения — `decisions.md §7.7`.

Исполнитель теперь может: писать миграции в `supabase/migrations/`, применять их **к локальной** базе, перегенерировать `src/types/database.types.ts` командой `pnpm db:types`, писать сервисы, хуки запросов и мутаций, схемы zod.

**Что остаётся за владельцем:**

- `npx supabase db push` — выкатка миграций в облако. Это рабочая база семьи; исполнитель останавливается и сообщает, что миграцию пора выкатить.
- `.env`, `.env.development`, `.env.production`, `.env.test` — адреса и ключи окружений.
- Дашборды Supabase и Cloudflare.

**Правила, которые не отменяются вместе с разделением:**

- **Многошаговые записи — функцией в базе через `rpc`**, а не цепочкой запросов: PostgREST даёт одну транзакцию на запрос, и отказ посередине оставляет половину записи. Образец — `supabase/migrations/20260919051102_create_product_with_variant.sql`: `security invoker`, `set search_path = ''`, `revoke` у `public` и `anon`, `grant` для `authenticated`.
- **Применённую миграцию не редактировать** — только новая миграция. Проверить, применена ли: `npx supabase migration list`.
- **Новая таблица — три пункта:** `enable row level security`, политика, `grant`. Удаление (`DELETE`) для архивируемых сущностей не выдаётся.
- **Форма сущности в кэше изменилась — поднять `CACHE_BUSTER`** в `src/constants/caching.constants.ts`.
- **Схема ввода и интерфейс сущности связаны через `satisfies z.ZodType<…>`.**

## Локальное окружение

**Облако — рабочая база семьи, в ней живые рецепты. Тестовые данные туда не пишутся никогда.** Любая живая проверка — только на локальном стеке.

| Команда | Куда смотрит |
|---|---|
| `pnpm dev` | локальный Supabase (`.env.development`) |
| `pnpm build`, `pnpm preview` | облако (`.env.production`) |
| `pnpm dev:prod` | дев-сервер против облака — только посмотреть, ничего не записывая |

**Перед живой проверкой — убедиться, что окружение поднято, и поднять самому.** Владелец может забыть запустить Docker или стек; останавливаться и спрашивать из-за этого не надо.

1. `docker info`. Ошибка — Docker не запущен: `Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"` (PowerShell) и повторять `docker info`, пока не ответит; обычно до пары минут.
2. `npx supabase status`. Стек не запущен — `npx supabase start`.
3. В `product_categories` пусто — накатить дев-данные: `docker exec -i supabase_db_recipe-book psql -U postgres -d postgres < supabase/dev-data.sql`. Запускать скрипт можно, править — нет.
4. Вход в приложение: **`dev@recipe-book.local` / `devpass123`**, пользователь только локальный. Нет такого (после сброса базы) — создать одним запросом, регистрация на локальном стеке открыта:

   ```bash
   curl -s -X POST "http://127.0.0.1:54321/auth/v1/signup" -H "apikey: sb_publishable_ACJWlzQHlZjBrEguHvfOxg_3BJgxAaH" -H "Content-Type: application/json" -d '{"email":"dev@recipe-book.local","password":"devpass123"}'
   ```

**Новую миграцию к локальной базе** применять через `npx supabase migration up` — она накатывает только непримененные и не трогает данные. `npx supabase db reset` стирает локальную базу целиком: после него заново накатить `dev-data.sql` и создать дев-пользователя (шаги 3–4).

**Нельзя:** `npx supabase db push` (облако — только владелец) и `npx supabase stop --no-backup` (стирает локальные данные без нужды). Писать в локальную базу через приложение можно сколько угодно — для этого она и есть.

## Как выполнять фазу

По умолчанию одна сессия — одна фаза.

**В обычной сессии** владелец может явно попросить несколько подряд («сделай фазы 2–3») — тогда они выполняются последовательно, но правила ниже применяются к **каждой** отдельно: свой список файлов, свой прогон раздела «Проверка», своя запись в `EXECUTION.md`. Итог по каждой фазе отдельным блоком, не одним общим «готово».

**Через скилл `frontend-run`** — строго одна фаза за вызов, это заложено в самом скилле. Несколько фаз = несколько вызовов.

**Первая же непройденная проверка останавливает всю цепочку.** Не переходить к следующей фазе, чтобы «починить потом»: следующая будет строиться на сломанном основании, и разбирать придётся два слоя вместо одного.

Протокол фазы:

1. Прочитать `decisions.md` и раздел нужной фазы в плане целиком.
2. Делать **только эту фазу**. Файлы, не перечисленные в её списке, не трогать. Заметил нужную правку за пределами фазы — сказать об этом, а не делать молча.
3. В конце пройти по пунктам раздела **«Проверка»** этой фазы и отчитаться по каждому: выполнено или нет, с фактическим выводом команд. Не отчитываться об успехе там, где не проверял.
4. **Не коммитить.** Изменения остаются в рабочем дереве — их смотрит и коммитит владелец проекта.

Если план расходится с реальностью (не существует того, на что он ссылается; шаг противоречит другому решению; выясняется, что задумка не работает) — **остановиться и спросить**. Не изобретать обходной путь молча: план правится осознанно, через дополнение в разделе «Дополнения».

## Жёсткие инварианты

Нарушение любого из них — дефект, даже если код работает.

- **Вся арифметика КБЖУ живёт только в `src/domain/nutrition/`.** Ни один компонент, хук или репозиторий не считает питательность сам. Модуль не импортирует React, Supabase и Mantine — он должен запускаться в Node без DOM.
- **Удалений нет.** Только `archived_at`. Никаких `DELETE` из приложения ни по одной сущности.
- **Молчаливых нулей не бывает.** Продукт без КБЖУ даёт запись в `incompleteProducts` и видимое предупреждение в UI, а не ноль в сумме.
- **Округление только при отображении.** Домен возвращает сырые числа: ккал до целых и БЖУ до одного знака — работа UI.
- **Сгенерированная форма строки не выходит за слой сервисов.** `src/api/services/` отображает строку из `database.types.ts` в доменную сущность: camelCase, только нужные поля, вложенные связи разрешены. Числовые колонки при этом сверяются с фактическим ответом — строкочисел за этой границей быть не должно.
- **Даты `cooked_at` / `finished_at`** — строки `YYYY-MM-DD`. Никаких `Date` и часовых поясов.
- **Приоритет у iOS.** Основной пользователь на iPhone. Расхождение поведения между платформами решается в пользу Safari на iOS. Только `100dvh`, `env(safe-area-inset-*)`, tap targets ≥44px.
- **Новые зависимости — только с разрешения.** Стек зафиксирован в `decisions.md §2`. Понадобилось что-то ещё — спросить.
- **Данные загружаются в клиент целиком.** Никаких серверных endpoint'ов поиска, никакой пагинации, никакой фильтрации на стороне БД. Поиск и фильтры — по датасету в памяти.

## Команды

Заполняются по мере появления (Фазы 1–2). Ожидаемый набор:

```
pnpm dev            # дев-сервер против локального Supabase
pnpm dev:prod       # дев-сервер против облака — только смотреть
pnpm build          # прод-сборка
pnpm lint           # линт
pnpm test           # vitest
pnpm db:reset       # пересоздать локальную БД из миграций + seed
pnpm db:types       # перегенерировать src/types/database.types.ts
```

После правки схемы БД **всегда** перегенерировать типы — руками `database.types.ts` не редактировать.

## Чего в проекте нет

Не предлагать и не добавлять по своей инициативе: SSR, серверный код помимо Supabase Edge Functions, мультипользовательность и роли, миллилитры и конверсии единиц, десктопный layout (одна колонка `max-width: 600px`), офлайн-запись. Обоснования — в `decisions.md`.
