#### Conflicting rules: Russian `raise` messages in non-migration SQL
- [plan] The plan contradicts itself for `supabase/demo/setup.sql:29`, `supabase/demo/setup.sql:132` and `supabase/dev-data-cleanup.sql:35` (Russian `raise exception` / `raise warning` literals).
  - (a) Common decision 9 says developer-facing messages (`throw new Error`, `console.*`) are translated with the comments; the only exception named is strings compared against the database. These three are operator-facing messages and are compared against nothing.
  - (b) The L7 Stop condition says the Cyrillic search shows data-only hits.
  - (c) L7 step 1 and the Stop condition require strip-and-compare to be identical for `setup.sql` and every `.sql` file in scope, and the check keeps string literals, so translating a message fails it.
  - The developer chose (c) over (a)/(b) and escalated. That is the right call, but the plan needs an amendment.
- Is the check meant to cover these files? Not by its rationale. "Migration comments" defines it as protection against a logic change slipping silently into an applied migration (migrations are tracked by file name and never re-applied, so a hidden change never reaches prod). That does not hold here. `setup.sql` is re-runnable by design ("Re-running is safe") and lives outside `supabase/migrations/`; `dev-data-cleanup.sql` is a local hand-run script. A changed message there is not a silent logic change: the file text is what runs. `setup.sql:29` and `dev-data-cleanup.sql:35` run straight from the file text; `setup.sql:132` sits inside `demo.reset()`, so it behaves like the `backup_export_import` in-body comments the plan already accepts (the demo DB keeps the Russian text until `setup.sql` is next re-applied: invisible and harmless). All 10 migrations contain zero Cyrillic literals (verified), so the check can stay fully strict for migrations.
- Recommended resolution (smallest amendment): translate the three messages, and amend L7 so strip-and-compare for `setup.sql` and `dev-data-cleanup.sql` compares modulo an explicit allowlist of exactly those three string literals (replace each listed literal with a placeholder on both sides; any other difference still fails). Migrations and `dev-data.sql` stay strictly literal-for-literal. Then update the quotes in `supabase/demo/DEPLOY.md` (`:61`, `:204`, `:205` quote the "this is not a demo project" message; `:209` paraphrases the `demo.reset` warning) to the new English text, per the L5/L6 amendment rule "the quoting file keeps its language, only the quoted message changes". About one more small L7 iteration (3 SQL lines plus about 4 doc lines).
- Alternative if the owner prefers not to touch them: record the three literals as a named exception in Common decision 9 and the L7 Stop condition and leave them Russian; the DEPLOY.md quotes then stay correct. Less consistent (the other developer messages in this phase, in `keepalive.ts`, `upload-photos.mjs`, `_build.ts`, are English) but zero risk.
