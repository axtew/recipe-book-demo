## Summary
Фаза 7 (`ProductPicker` / `ProductFormSheet` / `VariantFormSheet` / общий `SBottomSheetDrawer`) реализована по плану, работа с owner-only зоной не выходит за разрешённую однотабличную мутацию `addProductVariant`, жёсткие инварианты (нет удалений, null вместо тихих нулей, округление не в домене) соблюдены. `pnpm lint` и `pnpm build` перепроверены — чисто, совпадает с отчётом. Основные находки: явная ссылка на номер фазы в продуктовом коде-комментарии, неверное по факту описание дублирования поиска (полноценно дублируется весь `filterProducts`, а не только `normalizeSearch`, которая к тому же экспортирована — комментарий утверждает обратное), и форма-логика двух листов не вынесена в колокейтед-хук вопреки уже установленному в проекте паттерну `_useLoginForm.ts`. Отдельно — пункт проверки плана «закрывается по свайпу вниз» технически недостижим выбранным примитивом без внебюджетной работы; разработчик честно это задокументировал, но это гэп самого плана.

## Issues

### Code issues

#### Comments — pipeline residue
- [code] `src/components/ProductPicker/_helpers.ts:7-10` — комментарий к `normalizeQuery` ссылается на «Фаза 10 плана»: `а Фаза 10 плана явно сводит нормализацию поиска в общий src/utils/search.ts`. Продуктовый код не должен содержать номера фаз/ссылок на план (явное требование задачи и общая конвенция комментариев) — это переживёт контекст и станет непонятным упоминанием после того, как план исполнится или изменится. Убрать ссылку на фазу, оставить только техническую причину (что уже дублируется и почему сейчас не консолидировано), не привязываясь к нумерации.

#### DRY / same-area precedent
- [code] `src/components/ProductPicker/_helpers.ts:7-8` — комментарий утверждает, что `normalizeSearch` из `src/pages/ProductsPage/_helpers.ts` «не экспортирована за пределы своей страницы» — это фактически неверно: `src/pages/ProductsPage/_helpers.ts:16` — `export function normalizeSearch(...)`. Тот же файл экспортирует ещё и готовую `filterProducts` (`src/pages/ProductsPage/_helpers.ts:23`, включает и архивный фильтр, и нормализацию, и `includes`) — то есть переиспользуемая функция уже существует и доступна за пределами страницы, а не только «не экспортированная» вспомогательная функция. Комментарий, утверждающий несуществующее свойство кода, сам по себе дефект независимо от корректности поведения.
- [code] `src/components/ProductPicker/_ProductPicker.tsx:55-60` — дублирует не только нормализацию, а всю логику `filterProducts` (архивный фильтр + `normalizeQuery` + `includes`) построчно один в один с `src/pages/ProductsPage/_helpers.ts:23-30`. Поскольку `filterProducts`/`normalizeSearch` уже экспортированы, по лестнице размещения («сущность поднимается на общий уровень, когда появляется второй реальный потребитель») появление второго потребителя (`ProductPicker`) — сигнал поднять функцию, а не тихо реплицировать её тело с локальной копией нормализации. Если правка `ProductsPage/_helpers.ts` вне списка файлов фазы — это стоило прямо назвать как «нужна правка за пределами фазы» (протокол CLAUDE.md), а не описывать как частичное дублирование одной вспомогательной функции.

#### Component size / separation of concerns
- [code] `src/components/ProductFormSheet/_ProductFormSheet.tsx:28-87` и `src/components/VariantFormSheet/_VariantFormSheet.tsx:25-78` — состояние формы (5-6 `useState`), синхронизация сброса при открытии и вся валидация+сборка пейлоада через zod прямо в теле компонента. В проекте уже есть прецедент ровно этой формы — `src/pages/LoginPage/_useLoginForm.ts`, куда вынесены состояние формы и `handleSubmit`, оставляя компонент JSX+глиной. Конвенция «Component size» прямо требует: «Data fetching, derivation, transforms, and non-trivial helper logic belong in the colocated hook… never inline in the render body». Оба новых листа этому прецеденту не следуют — стоит вынести в `_useProductForm.ts` / `_useVariantForm.ts` рядом с компонентами.

### Plan issues

#### Verification item unachievable with chosen primitive
- [plan] `plans/recipe-book-v1/plan.md:684` — пункт «Проверка» Фазы 7 требует, чтобы лист «закрывался по свайпу вниз», но `@mantine/core`/`@mantine/hooks` (используемая версия) не содержат жеста свайпа для `Drawer` — сам разработчик это подтвердил (`plans/recipe-book-v1/EXECUTION.md:471`, `grep -rli swipe` по обоим пакетам — пусто) и честно отметил пункт как «⚠️ частично». Тот же примитив уже используется в `ArchiveConfirm` (Фаза 6), и там свайп не заявлялся в её собственной проверке. Реализация требует отдельного жестового хука вне списка файлов и бюджета (`ui`, 7 операций) этой фазы и затрагивает уже существующий `ArchiveConfirm`. Нужна осознанная правка плана — либо снять требование свайпа из проверки Фазы 7 (раз оно не было заложено в Фазе 6, установившей примитив), либо завести отдельный пункт/фазу под общий touch-gesture хук для всех нижних листов с бюджетом под него.
