## Notes

**Миграция supabase/migrations/20261021090000_backup_export_import.sql: замечаний нет, детали проверки:**
- Образец проекта выдержан: security invoker, пустой search_path, схемы в именах, revoke от public и anon, grant для authenticated. DELETE нигде нет. Файл новый, правок применённых миграций нет.
- Выгрузка: один SQL-оператор, один снимок; результат скаляр jsonb, max_rows не обрезает.
- Проверка пустоты и вставки в одной транзакции, под lock table (share row exclusive) по четырём таблицам. Права на LOCK у authenticated есть (UPDATE выдан на все четыре таблицы).
- Порядок вставки соответствует FK: категории, продукты и варианты (составной FK active_variant_id отложен), рецепты, затем шаги, связи категорий, ингредиенты (составной FK pinned_variant_id на пару product_id + id удовлетворён, потому что варианты уже в таблице), журнал. Архивные строки входят: фильтра по archived_at нигде нет.
- **Перезапись PK категории по совпадению имени безопасна.** На категории ссылаются только products.category_id и recipe_dish_categories.dish_category_id (оба on delete restrict, без on update cascade). Проверка пустоты считает все products (включая архивные) и все recipes; recipe_dish_categories не существует без рецепта, поэтому на "пустой" базе ссылающихся на категории строк нет, а блокировка не даёт им появиться между проверкой и обновлением. Если бы ссылка нашлась, UPDATE упал бы на FK (NO ACTION): отказ, а не порча данных. Альтернатива (оставить id базы и переписать ссылки в файле) сложнее и ломает "один в один" по id; без права DELETE другого простого пути нет. Текущее правило оправдано, оставить.
- Остаточные края, не блокирующие: на сервере файл не валидируется (вся валидация на клиенте; базу защищают check-ограничения и FK, ошибка уйдёт как importFailed); предел numeric(4,2) у multiplier схема не повторяет; для файла на порядки больше нынешнего стоит проверить statement_timeout (как в отчёте).
