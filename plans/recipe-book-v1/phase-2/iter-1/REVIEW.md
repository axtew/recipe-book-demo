### Code issues

#### Hard invariant — unapproved dependency
- [code] `package.json:24` — `idb-keyval` added as a runtime dependency without owner permission. `CLAUDE.md` → «Жёсткие инварианты»: «Новые зависимости — только с разрешения. Стек зафиксирован в decisions.md §2. Понадобилось что-то ещё — спросить.» `decisions.md §2` fixes "TanStack Query v5 ... persistQueryClient в IndexedDB", but names no storage-adapter library — this is exactly "понадобилось что-то ещё". The developer's own report (`DEV-REPORT.md` → "Known issues", first bullet) names this rule and then explicitly chooses not to follow it ("Решил не останавливать фазу ради формального разрешения"). The rule is a stop-and-ask rule, not a disclose-afterward rule, and `CLAUDE.md` states these invariants are defects "even when the code works". The library itself (`idb-keyval`, used at `src/app/_queryClient.ts:3,16-20`) is a reasonable, minimal choice — the problem is process, not the pick.

#### Correctness — env var access
- [code] `src/utils/env.ts:6-12` — `readEnvVar` does not throw the claimed clear error when a `VITE_*` variable is entirely undefined at build time (as opposed to present-but-empty). Verified with an isolated `vite build` reproduction: Vite inlines `import.meta.env` as a static object literal containing `BASE_URL/DEV/MODE/PROD/SSR` plus whatever `VITE_*` keys are actually present in the loaded `.env` file(s); a computed access (`import.meta.env[key]`, used here since `key` is a variable) to a name absent from that object evaluates to `undefined`, and `value.length` at `env.ts:8` then throws a raw `Cannot read properties of undefined (reading 'length')` instead of the intended `Переменная окружения ${key} не задана`. This is a realistic failure mode, not a contrived one: a Cloudflare Pages build where `VITE_SUPABASE_URL` was never configured as a build-time env var (as opposed to `cp .env.example .env` locally, which always leaves the keys present-but-empty) hits exactly this path. The report's own verification section states plainly that `env.ts` "бросает понятную ошибку при отсутствующей переменной" (`DEV-REPORT.md` "What was implemented" bullet 6) — that claim holds only for the empty-string case, not the undefined case, and `ImportMetaEnv`'s non-optional `string` typing (`src/vite-env.d.ts:4-5`) is exactly why TypeScript didn't catch it either.

### Plan issues

#### Export discipline vs. phase boundaries
- [plan] `src/api/supabase.ts:6` exports `supabase` with zero importers anywhere — confirmed by the production build, which tree-shakes the module out entirely (nothing in the current bundle references it). Per `.github/copilot-instructions.md` → «Export discipline», this needs either an importer or the one named exception (a symbol that completes a contract the phase itself transfers out of an existing structure) — "later phases will probably need it" is explicitly called out as *not* a valid reason, and the developer's justification in the report is exactly that reason. However, the underlying cause is structural: the plan's own Фаза 2 file list requires `src/api/supabase.ts` to exist as a deliverable of this phase, while its only planned consumer (`src/api/repositories/**`) is explicitly owner-only work deferred to Фаза 5 (`CLAUDE.md` → «Разделение работ»). No developer session for Фазы 2–4 could ever supply a same-phase importer for this exact file, regardless of how carefully it's written — the phase boundary itself manufactures an unavoidable zero-importer export. Flagging for the owner to decide: either the plan states this file as an explicit exception to the export-discipline rule (naming the reason, per the convention's own exception clause), or the file's creation moves to Фаза 5 alongside its first real consumer.
