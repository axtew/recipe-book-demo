### Plan issues

#### Verification item describes an unreachable check
- [plan] `plans/recipe-book-v1/plan.md:515` — «сборка с намеренно убранной переменной `VITE_SUPABASE_URL` падает с сообщением … а не с `TypeError`» is unsatisfiable as literally written, for two independent reasons, and the second one is more important than the build-vs-runtime ambiguity the developer's report focuses on:
  1. **Build vs runtime.** `vite build` for this SPA only transforms/bundles; it never executes application code, so it cannot itself "fail" from a thrown `Error`. The developer's report correctly identifies this and substitutes executing an SSR bundle of `env.ts` in Node — that part of the substitution is a defensible reading of an ambiguous instruction.
  2. **Reachability — the more important gap.** Even running the *real* built app (not a synthetic single-file SSR bundle) would not trigger this check at all right now. `src/api/supabase.ts:6` is the only importer of `src/utils/env.ts` (confirmed by grep across `src/`), and `src/api/supabase.ts` itself has **zero importers anywhere in the live import graph** — `src/main.tsx` → `src/app/App.tsx` / `src/app/providers.tsx` never reaches it. This is exactly what the plan's own named export exception at `plan.md:513` admits: "первый [потребитель] появляется в Фазе 3". So the module tree containing `readEnvVar` is dead code from a runtime-execution standpoint until Фаза 3 wires in `useAuth` — deleting `VITE_SUPABASE_URL` today and opening the actual app in a browser would show no error whatsoever, because the code that would throw is never evaluated.

  Given (2), the developer's chosen substitution — bundling and executing `env.ts` in isolation — is not a shortcut around a satisfiable check; it is the *only* way to exercise `readEnvVar`'s contract at all in this phase, because the integrated path the plan's wording implicitly assumes does not exist yet. That is a plan gap, not a developer shortcut: the checklist item should either (a) explicitly prescribe isolated execution of `env.ts`/`readEnvVar` (e.g. via a small Node/SSR harness, which is what the developer improvised) as the Фаза-2 check, and move the true end-to-end "app fails to boot without the var" check to Фаза 3 once `useAuth` actually imports `supabase`, or (b) state plainly that Фаза 2 can only unit-verify the function in isolation and the integration check is deferred. As currently worded, a future strict reading of "сборка ... падает" against the *real* app would report false success (nothing throws) even with the current code fully correct, which is worse than the ambiguity itself.
