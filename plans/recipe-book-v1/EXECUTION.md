# Журнал выполнения — recipe-book-v1

Одна запись на фазу. Заполняет исполнитель в конце фазы, до передачи владельцу на ревью.
Нужен, чтобы следующая сессия видела фактическое состояние, а не только план.

Формат записи:

```
## Фаза N — <название>

- **Дата:** YYYY-MM-DD
- **Статус:** выполнена | выполнена с отклонениями | остановлена
- **Модель:** sonnet-5 | opus-5
- **Файлы:** что реально создано и изменено
- **Проверка:** по каждому пункту раздела «Проверка» из плана — результат с фактическим выводом команд
- **Отклонения от плана:** что сделано иначе и почему. Пусто — так и написать
- **Замечено вне фазы:** найденное, но не тронутое (чужие файлы, будущие фазы)
```

### Дефект RLS-1 — блокирующий

RLS включена на всех 8 таблицах, но **политика создана только для `products`**. Фактическое состояние:

```
 table              | rls_on | policies
--------------------+--------+----------
 cook_logs          | t      |        0
 dish_categories    | t      |        0
 product_categories | t      |        0
 product_variants   | t      |        0
 products           | t      |        1
 recipe_ingredients | t      |        0
 recipe_steps       | t      |        0
 recipes            | t      |        0
```

Включённая RLS без политики закрывает таблицу **полностью, в том числе для залогиненного пользователя**. То есть приложение увидит пустые списки везде, кроме продуктов, и без единой ошибки в консоли — просто пустота.

Причина — формулировка в `phase-1-tutorial.md`: там был показан один пример политики и приписка «и так для каждой таблицы». Обучалка исправлена, политики выписаны все восемь явно.

**Не закрыв это, к Фазе 5 переходить нельзя.**

### Дефект SEED-1

`reference_data.sql` содержит только 5 продуктов из примера обучалки, комментарии-заглушки `-- ... остальные` остались на месте. План требует 50–80. Фазы 6+ (справочник, автодополнение продуктов) на пяти продуктах бессмысленно проверять.

### Дефект GRANT-1 — найден при проверке RLS, серьёзнее первого

При проверке через API запрос вернул не пустой массив, а `42501 permission denied for table`. Причина глубже забытых политик: у ролей `anon` и `authenticated` **нет прав `SELECT` / `INSERT` / `UPDATE`** на таблицы проекта — только служебные `REFERENCES` / `TRIGGER` / `TRUNCATE`.

То есть доступ проходит две независимые проверки — грант, затем политика RLS, — и запрос отбивался на первой. Даже `products` с корректной политикой отдавал бы `permission denied`. В обучалке этого шага не было вообще, добавлен раздел 3.9.1.

### Исправление — миграция `20260817172518_policies_dish_categories_cleanup`

Написана и применена локально 2026-08-18. Содержит:

1. **7 недостающих политик RLS** — дефект `RLS-1`.
2. **Гранты для `authenticated`** — дефект `GRANT-1`. Выданы избирательно: `select, insert, update` на архивируемые сущности и категории, плюс `delete` только на `recipe_steps`, `recipe_ingredients`, `recipe_dish_categories`, `cook_logs`. Роли `anon` не выдано ничего. Инвариант «удалений нет» стал невыполнимым действием, а не соглашением.
3. **`recipe_dish_categories`** — связь много-ко-многим (Р-5), столбец `recipes.dish_category_id` удалён.
4. **Очистка предзаполненных продуктов** — решение владельца заполнять справочник вручную. Порядок операций важен: `fk_active_variant` объявлен `on delete restrict`, а RESTRICT в Postgres проверяется немедленно и не отсрочивается даже у `deferrable` ограничения, поэтому сначала снимаются ссылки на активные варианты, потом удаляются варианты.
