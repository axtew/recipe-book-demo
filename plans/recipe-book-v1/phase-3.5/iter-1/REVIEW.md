Фаза 3.5 (code-based роутинг + семейство Typography) реализована аккуратно и по существу совпадает с целью плана: `pnpm lint`/`pnpm build`/`pnpm test run` перепрогнаны лично ревьюером и чисты (совпадает с отчётом разработчика), guard в `beforeLoad` корректен и не даёт вспышки защищённого экрана, все файловые удаления полные, `pnpm format` реально скоупнут на `src`, `EXECUTION.md` дописан строго добавлением (проверено `git diff HEAD`). - [code] `src/components/Typography/index.ts:5` — `export type { TTextColor } from "./_BaseText";` не имеет ни одного импортёра вне `Typography/` (проверено `grep` по `from "@/components/Typography"` — все три потребителя берут только `B1/B2/B3/H1/Caption2`, ни один не импортирует `TTextColor`). Именованное исключение по экспорту в отчёте разработчика покрывает компоненты (`H2`, `H3`, `Caption1`, `Num1`, `Num2`) с явно названными будущими потребителями, но не этот тип — по конвенции («Barrel — a line goes in when a consumer outside the folder imports it») баррель-строка для `TTextColor` лишняя до появления первого внешнего потребителя.

#### Comments
- [code] `src/hooks/useAuth.hook.ts:9` — JSDoc `вызывается из beforeLoad корневого роута` стал недостоверным именно в результате этой фазы: `getAuthSession()` теперь вызывается из `beforeLoad` **layout-роута защищённой части** (`protectedLayoutRoute`, `AppRouter.tsx:25`) и из `beforeLoad` **роута логина** (`loginRoute`, `_routes.tsx:28`) — ни один из них не является «корневым роутом» (`rootRoute = createRootRoute()` вообще не имеет `beforeLoad`). До Фазы 3.5 при file-based роутинге это могло быть точным (guard действительно жил в `__root.tsx`); после перевода на code-based комментарий описывает архитектуру, которой больше нет. Файл входит в список правок этой же фазы (добавлена ветка `console.warn`), так что actuализировать комментарий рядом было уместно сделать в этом же изменении.

## Notes (optional)

- **Циклический импорт `AppRouter.tsx` ↔ `_routes.tsx` — признан обоснованно.** Буквальная форма плана (`_routes.tsx` экспортирует готовые массивы `commonRoutes`/`protectedRoutes`, а `AppRouter.tsx` держит `rootRoute`/`protectedLayoutRoute`) действительно даёт циклическую ES-модульную зависимость: `_routes.tsx` должен был бы импортировать `rootRoute` из `AppRouter.tsx` в момент top-level вызова `createRoute({ getParentRoute: () => rootRoute })`, а `AppRouter.tsx` — импортировать готовые массивы из `_routes.tsx` раньше, чем успеет выполниться его собственный `const rootRoute = createRoute...`. Это классический half-initialized-module кейс, а не надуманная причина. Фабричные функции `createCommonRoutes(rootRoute)` / `createProtectedRoutes(protectedLayoutRoute)`, принимающие родителя параметром, — минимальное решение при том ограничении, что план сам явно требует держать `rootRoute`/`protectedLayoutRoute` в `AppRouter.tsx` (перенос их в `_routes.tsx` решил бы цикл, но нарушил бы это явное требование плана). Разработчик раскрыл отклонение и в отчёте, и в `EXECUTION.md` — по правилам ревью этого достаточно, чтобы не считать это дефектом кода. Единственное, чего не хватает, — сам `plan.md` (раздел «Дополнения») не обновлён этим фактом; Фазы 8/9 по тексту плана «добавляют роуты в `_routes.tsx`» и должны знать, что там теперь фабрики, а не статичные массивы. Стоит дописать это в «Дополнения» при следующей правке плана — не блокирует фазу.
