#### Styling / Mantine theme

- [code] `src/theme/_GlobalStyle.ts:22-32` — размер ячейки дня обходит тему: селектор `.${Day.classes.day}.${Day.classes.day}` привязан к CSS-module хешу (`m_396ce5cb`, меняется между версиями Mantine) и держится на хаке специфичности; плюс `_GlobalStyle.ts` теперь импортирует `Day` из `@mantine/dates` ради одного имени класса. План требует «в теме», а поддерживаемый путь есть. Проверено по установленным исходникам 9.7.3:
  - `Day` вызывает `useStyles({ name: __staticSelector || "Day", ... })`, а `Month`/`DatePicker`/`DatePickerInput` передают `__staticSelector` = `"DatePicker"` / `"DatePickerInput"`. Значит `useStyles` внутри `Day` берёт `theme.components.DatePicker(Input).styles` и применяет их к ячейке (`use-styles.mjs`: `resolvedThemeStyles` по `themeName`). Именно поэтому `Day.extend` не срабатывает — и именно поэтому срабатывает `styles` на родителе.
  - В `getStyle` порядок слоёв: стили темы -> `styles` -> `vars` -> `style`. Инлайновый `--day-size` из `varsResolver` перебить через `styles` нельзя, но он равен `var(--day-size-sm|md)`, а эти переменные объявлены на том же элементе в классе (`styles.css`, `.m_396ce5cb`). Инлайновое значение из `styles.day` выигрывает у класса без всякой специфичности.
  - Типизация не мешает: значение `styles` — `CSSProperties` Mantine с индексной сигнатурой `[key: string]: any`, ключ `day` есть у обоих компонентов (в отличие от `vars`, где у `DatePicker` ключа `day` нет — это и упёрлось в отчёте).
  - Как должно выглядеть (описание, не правка): в `_mantineTheme.ts` у `DatePicker.extend` — `styles: { day: { "--day-size-sm": rem(TAP_TARGET_PX) } }`, у `DatePickerInput.extend` (рядом с уже имеющимся `modalProps`) — `styles: { day: { "--day-size-md": rem(TAP_TARGET_PX) } }`. Тогда `TAP_TARGET_PX` уже на месте, `_GlobalStyle.ts` и импорт `Day` откатываются к виду до итерации 2, а размер лежит там, где его ищет читатель. Запасные поддерживаемые варианты: `getDayProps: () => ({ size: ... })` в `defaultProps` (`Month` распространяет `...dayProps` после `size`) либо статический класс `mantine-DatePicker(Input)-day` через `&&` по прецеденту `BottomSheetDrawer` — но первый вариант чище.
  - Исправить нужно и потому, что, как показано выше, комментарий в `_GlobalStyle.ts:24-27` («тема до ячейки не достаёт: вложенные компоненты берут имя у календаря-родителя») утверждает обратное тому, как устроен Mantine: имя родителя как раз и делает тему достижимой. Комментарий, заявляющий свойство, которого нет, — отдельное замечание конвенции «Comments». После переноса в тему этот комментарий уходит, а в теме нужен короткий: что размер ячейки поднят до тап-цели и что `sm` — размер `DatePicker`, `md` — `DatePickerInput` (почему именно эти переменные, ради которых они разные, — одна строка).
  - Важное ограничение к варианту выше: подставляются только `--day-size-sm` / `--day-size-md`; если когда-нибудь у календарей появится другой `size`, правка его не покроет. Сейчас используются ровно `DatePicker` (размер по умолчанию `sm`) и `DatePickerInput size="md"` — покрыто.

## Оценка отклонений, о которых просили

- **`modalProps: { xOffset: 0, padding: 2 }` на `DatePickerInput` в теме.** Приемлемо. Это штатные пропсы `Modal` (`--modal-x-offset`, `padding`), лежат в теме, а не у потребителя; один потребитель (`CookLogSheet`) модальный, `modalProps` у него не переопределяются (иначе тема-дефолт был бы затёрт, но сейчас нет). 2px вместо 0 — чтобы граница модалки не обрезалась; значение наследует ограничение: календарь прижат к краям на 320px (2.5-317.5px по отчёту). Это следствие самого требования «ячейка 44px, неделя целиком на 320px» (7x44 = 308px + зазоры), чище нельзя без уменьшения ячейки, а инвариант «тап-цель >= 44px» важнее запаса по краям. Не блокирует.
- **`margin-inline: -12px` у `SPicker`.** Допустимо, но хрупко: число зависит от внутреннего отступа `Drawer` (16px) и от ширины месяца (~312px), и ни то ни другое в коде не привязано. На экранах шире 320px безвредно (контейнер центрируется), поэтому не блокирует. Альтернативы чище не видно: само требование — календарь шире, чем область контента листа на 320px; комментарий у `SPicker` честно объясняет причину. Если число придётся менять, править в одном месте.
- **Удаление шести явных `hideControls`.** Корректно: `NumberInput.extend({ defaultProps: { hideControls: true } })` в теме применяется ко всем потребителям, явных пропсов нигде не осталось (`grep hideControls src` — одно вхождение в теме). Прямого переопределения (`hideControls={false}`) нигде нет — приемлемо.
- **`IngredientOptionsSheet`.** `SSheetField` из `@/components/SheetForm`, импорт `SField` из стилей редактора убран, `SSheetBody` из локальных стилей удалён вместе с использованием, `_styles.ts` содержит только используемые экспорты. `SField` в `LoginPage` и `RecipeEditorPage` остаются осознанно (вне объёма итерации).
